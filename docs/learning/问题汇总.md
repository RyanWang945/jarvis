# jarvis 问题和设计思路汇总

## 架构设计问题
### 对于long run 全能的agent，应该选择怎样的架构。这里经过3次演变。
#### 第一版
使用caagent 制定work plan，设定每个task 的目标交给多个worker 做，然后后置的校验模块校验是否完成，caagent评估是否完成。
第一版出了非常多的问题，流程过重，跑起来都费劲。架构相比开源实现不简洁。skill采取工具注入的形式，不简洁。
#### 第二版
主图 + 子图模式。主图负责意图识别，结果汇总，子图负责具体任务的执行，子图是一个react模式，循环完成任务。
这个的主要问题是，泛化能力差，比如对于查询任务完成的不错，但是对于deepresearch任务完成的不好。两个固定的工作流，一个主工作流，一个子工作流。

#### 第三版
当前的架构，conversation 层 + react 层，conversation 负责意图识别，选择工具，选择skill，react层负责reason act observe。skill加载采取只加载成prompt的形式，渐进式披露。
codex 工具变成代理全部代码和仓库任务的工具。
演进下来固化了多个概念，conversation指的是整个对话，turn代表一次用户请求触发的对话。
为了支持long run，在最开始增加了gateway层
总体变成了 飞书 - gateway - conversation - turn  gateway是为了可以处理定时任务，用户请求直接路由到底层agent，但是底层agent可能创建了定时任务，而gateway可以定时处理然后主动对飞书机器人推送消息。
同时gateway也可以加强jarvis的尝试运行能力，比如中断任务恢复，多任务排队等。


### 工具
第一版的工具注入就是罗列工具进去，但是测试中经常出现，比如代码任务选择bash来写，这里就将bash 去掉，。不开放bash。codex 工具能力变大，即全部代码相关任务都能用。
conversation层有一个runtimePolicy的层，预先意图分析时会指定某些模式下应该有什么工具，然后给react执行。
默认低权限可见                                                                                                                                         
- obsidian_wiki_query：查 Obsidian/wiki 长期记忆。
- business_knowledge_search：查 OpenSearch 业务知识库、研究材料、SEC 等。                                                                              
- tool_search：搜索隐藏工具候选，不执行、不授权；找不到时返回 no_capable_tool。 
- ask_user：低权限工具，模型觉得当前信息不够，需要问用户。
通过 intent/capability 或 tool_search 动态开放
- scheduled_task：创建、列出、删除提醒任务。现在用于 reminder scheduler。
- delegate_to_codex：交给 Codex 做本地注册 repo 的检查、diff、测试、改代码、提交/推送等。最近已加约束：轻量 repo inspect 也可以用，但最终必须总结成用户 可理解的解释，不能直接吐 raw stdout。
- tavily_search：联网搜索当前信息。
- obsidian_wiki_draft：创建 wiki 草稿。
- obsidian_wiki_apply：把 wiki 草稿应用到正式 wiki，需要用户确认。

已注册但目前不建议/基本隐藏                                                                                                                            
                                                                                                                                                         
  - delegate_to_claude_code：旧的高权限代码委托工具，exposed_to_llm=False，现在主要是兼容遗留。                                                          
  - shell_inspect：只读 shell 检查工具，代码里有定义，但当前 runtime policy 没把它放进默认暴露列表。                                                     
  - shell_run_command：执行单条本地命令，中风险，需要显式用户命令；当前 policy 也没默认开放。                                                            
  - write_file：向 Jarvis workspace 写 UTF-8 markdown，中风险；当前 policy 没默认开放。                                                                  
  - obsidian_wiki_maintain：wiki 维护检查工具，代码里注册了，但当前 policy 没开放。   

意图分析分析出需要提醒时，增加scheduled_task
用户明确要求写obsidian wiki时，增加obsidian_wiki_draft/apply工具
tool_search 搜索完工具后，runtime 还有校验，避免解锁高权限工具，这个校验怎么做的？

解决不出来任务时，直接总结并要求澄清问题。
