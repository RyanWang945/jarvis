Findings

  - High MySQL 初始化脚本会互相冲突，fresh Docker 初始化大概率失败。docker-compose.yml:13 会把整个 scripts/mysql-init 挂到 /docker-entrypoint-initdb.d，其中 scripts/mysql-init/001_schema.sql:100 和 scripts/mysql-init/001_v1_schema.sql:105 都已经创建了带 assistant_message_id/provider_tool_call_id/step_index
    的 tool_calls，但 scripts/mysql-init/002_tool_calls_audit_fields.sql:1 又无条件 ADD COLUMN 同名字段。按字母序执行会触发 duplicate column/key。
  - High KB API 暴露了任意本地路径读写/外部解析入口，且路由层没有鉴权或路径边界。app/knowledge_base/api.py:25 接受任意 file_path，服务层直接 Path(file_path) 读取 ingest；SEC parse 还接受任意 input_dir/output_dir 并写结果，app/knowledge_base/api.py:307、app/knowledge_base/service.py:341、app/knowledge_base/
    sec_parse.py:124。如果服务绑定到非 localhost 或被本机低权限进程访问，这是本地文件读取、写入和 API key 额度消耗风险。
  - Medium 飞书“回复 bot 消息触发继续对话”的分支实际上不可达。app/channels/feishu.py:268 传入了 reply_to_external_message_id，并在 metadata 写 reply_to_bot，但 app/channels/feishu.py:917 有 parent/root 时也固定返回 False。对应触发逻辑在 app/persistence/conversation_store.py:94 依赖
    metadata["reply_to_bot"]，所以群聊里直接回复 Jarvis 的消息不会唤起 agent，除非再次 @。
  - Medium API 契约和生产 MySQL store 不一致，缺失 conversation 时 list messages/turns 不会 404。app/api/agent.py:1087 和 app/api/agent.py:1096 期望 store 抛 KeyError 后转 404；但 app/persistence/conversation_store.py:203 和 app/persistence/conversation_store.py:213 直接按 conversation_id 查询并返回空列表。
    不存在的会话会被误报为“存在但无消息/无 turns”。
  - Medium 项目级测试入口不可复现。pyproject.toml 只有 pytest 依赖，没有 testpaths/norecursedirs 配置；直接跑 python -m pytest -q 会递归进入 data/，我这里在 data/artifact_previews/... 和 data/pytest-tmp 上 collection 阶段 PermissionError。限定 tests/ 后也被当前 temp/pycache 权限问题拦住，无法得到完整测试结
    果。
