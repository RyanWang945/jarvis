# Jarvis 观测驱动 E2E 测试集设计草案

日期：2026-07-02

## 1. 背景

Jarvis 的主要质量问题不只体现在最终回复，还体现在路由、planner skill 选择、plan 粒度、node runtime、artifact 交付和聚合策略上。纯手写测试集很难覆盖这些真实分布问题。

本设计的方向是：

```text
生产链路真实运行
-> 可观测记录 trace / log / raw_payload / session workspace
-> 按 conversation 汇总真实对话
-> 从某些 session / turn 提炼候选测试样本
-> 人工或规则确认成 curated E2E cases
-> 通过生产库和 HTTP/API 入口跑 E2E
-> E2E 只记录每轮高层结果和 trace_id
-> 具体工具调用和链路细节由 trace 负责回查
```

已有高层文档：`docs/design/2026-6/【2026-06-25】Jarvis Trace 驱动真实对话评测与优化闭环.md`。本文聚焦生产链路 E2E 测试集落地。

## 2. ID 模型

### conversation_id

数据库中的长期对话容器，对应 `conversations.id`。

用途：

- 聚合同一飞书私聊或群聊的多轮消息。
- 构造多轮上下文。
- 作为观测和评测的会话边界。
- trace 中可映射为 `langfuse.session.id = conversation:{conversation_id}`。

### turn_id

数据库中的一次 Jarvis 执行边界，对应 `turns.id`。

用途：

- 定位某一轮用户输入和 Jarvis 回复。
- 关联本轮 plan、execution_report、aggregation、tool calls、artifacts。
- E2E runner 的每轮主索引。

### session_id

Task runtime 为某个 turn 创建的本地工作区 ID，默认格式：

```text
sess_{turn_id}_{random_hex}
```

用途：

- 定位 `sessions/{session_id}/dag.json`。
- 定位 node result、provider logs、临时 artifacts。
- 隔离一次执行的文件系统产物。

在当前正常执行中，`turn_id` 和 `session_id` 基本是一对一；概念上仍然不同。`turn_id` 是业务事实，`session_id` 是执行产物定位。

### trace_id

一次可观测链路 ID。

用途：

- 回查 planner skill router、planner、node、tool、aggregator 等细节。
- E2E runner 必须记录每轮 `trace_id`。
- E2E 不需要重复保存所有工具细节，失败时通过 `trace_id` 定位。

## 3. 观测汇总层

目标是把生产运行记录汇总为机器可读的 observed turn/session 记录。

建议脚本：

```text
scripts/export_observed_sessions.py
```

输入来源：

- MySQL `conversations`
- MySQL `messages`
- MySQL `turns`
- MySQL `artifacts`
- turn final raw_payload
- `sessions/{session_id}/session.json`
- `sessions/{session_id}/dag.json`
- `sessions/{session_id}/nodes/*/result.json`
- trace/log 中的 trace_id

输出建议为 JSONL：

```json
{
  "conversation_id": 3332,
  "turn_id": 3320,
  "session_id": "sess_3320_51f39faaadfb",
  "trace_id": "41b9629c92d68a4800bec91b47040c9c",
  "user_input": "看看金价",
  "assistant_reply": "...",
  "status": "completed",
  "route": "planned",
  "selected_planner_skills": ["finance-analysis-planning"],
  "plan": {},
  "execution_summary": {
    "node_count": 1,
    "node_ids": ["collect_gold_price_evidence"],
    "node_modes": ["write"],
    "artifact_count": 0
  },
  "signals": {
    "maybe_overplanned": true,
    "unexpected_internal_artifact": "evidence_claims.md"
  }
}
```

这个文件是候选池，不直接作为正式测试集。

## 4. Curated E2E Case

从 observed records 中人工或半自动挑选稳定、有代表性的样本，生成 curated case。

建议路径：

```text
tests/fixtures/e2e_observed_cases/*.jsonl
```

单轮 case 示例：

```json
{
  "id": "simple_gold_price_quote",
  "source": {
    "conversation_id": 3332,
    "turn_id": 3320,
    "session_id": "sess_3320_51f39faaadfb",
    "trace_id": "41b9629c92d68a4800bec91b47040c9c"
  },
  "messages": [
    {"role": "user", "content": "看看金价"}
  ],
  "expect": {
    "required_status": "completed",
    "forbidden_planner_skills": ["finance-analysis-planning"],
    "max_nodes": 1,
    "allowed_node_modes": ["read"],
    "forbidden_artifacts": ["evidence_claims.md"],
    "reply_must_include_any": ["金价", "黄金"],
    "reply_must_not_include_any": ["报告已生成", "附件"]
  },
  "mode": {
    "production_db": true,
    "entrypoint": "api",
    "record_trace_id": true
  }
}
```

多轮 case 示例：

```json
{
  "id": "followup_uses_previous_topic",
  "messages": [
    {"role": "user", "content": "Python 的 GIL 是什么？简要解释。"},
    {"role": "user", "content": "那 3.13 有什么变化？"}
  ],
  "expect": {
    "required_status": "completed",
    "same_conversation": true,
    "turns": [
      {"reply_must_include_any": ["GIL"]},
      {"reply_must_include_any": ["3.13", "free-threading", "GIL"]}
    ]
  }
}
```

## 5. E2E Runner

E2E runner 应通过真实 API 入口触发，尽量与飞书触发流程一致。

建议脚本或 pytest：

```text
tests/test_observed_e2e.py
scripts/run_observed_e2e.py
```

执行原则：

- 使用生产库或生产同构库。
- 通过 HTTP/API 入口进入，不直接调用内部 planner。
- 使用专门的 e2e `external_chat_id` 和 `sender_id`。
- 每个 case 创建独立 conversation，除非 case 明确测试多轮上下文。
- 每轮记录 `conversation_id`、`turn_id`、`session_id`、`trace_id`、status、reply preview、关键断言结果。
- 工具调用细节不在 E2E result 中展开，由 trace 负责。

输出建议：

```json
{
  "run_id": "e2e_20260702_001",
  "case_id": "simple_gold_price_quote",
  "status": "failed",
  "turns": [
    {
      "turn_index": 1,
      "conversation_id": 9001,
      "turn_id": 3401,
      "session_id": "sess_3401_abcd1234",
      "trace_id": "....",
      "status": "completed",
      "checks": [
        {
          "name": "forbidden_planner_skills",
          "passed": false,
          "actual": ["finance-analysis-planning"]
        }
      ]
    }
  ]
}
```

## 6. E2E 断言边界

E2E 只断言高层行为，不重复 trace 的职责。

适合在 E2E 中断言：

- turn 是否完成。
- route 是否合理。
- 是否误选 planner skill。
- plan node 数量和 mode 是否合理。
- 是否产生不该产生的 artifact。
- 最终回复是否包含或不包含关键短语。
- 是否记录了 trace_id。

不建议在 E2E 中强断言：

- Tavily 具体返回了什么。
- LLM 中间推理文本。
- 每个工具调用的完整参数。
- token 数必须等于某个值。

这些细节应通过 trace 回查或在更低层测试中验证。

## 7. 生产库使用约束

如果 E2E 直接使用生产库，需要显式隔离。

建议：

- `external_chat_id` 前缀统一为 `e2e-`。
- `sender_id` 使用 `e2e-tester`。
- 每次运行写入 `test_run_id` 到 message/turn metadata 或 raw_payload。
- 默认不清理数据，保留为观测材料。
- 提供按 `test_run_id` 查询和归档能力。
- 对可能产生外部副作用的任务加 case 级开关，例如 `allow_external_delivery`、`allow_git_push`，默认 false。

## 8. 最小落地顺序

1. 先保证每个 turn 的 raw_payload 和 trace 中有 `conversation_id`、`turn_id`、`session_id`、`trace_id`。
2. 做 observed session/turn 导出脚本。
3. 手工挑 5-10 个真实问题生成 curated case。
4. 做 API 入口 E2E runner，只记录每轮结果和 trace_id。
5. 加结构断言：skill 选择、node mode、artifact、status。
6. 再考虑 LLM judge 或答案质量评分。

## 9. 待讨论问题

1. `trace_id` 的标准存放位置：是否应写入 turn final raw_payload 顶层，避免只能从日志反查。
2. E2E 是否必须走飞书 webhook payload，还是走当前 API/GatewayService 等价入口即可。
3. E2E 数据是否进入生产库，还是使用生产同构库。
4. case 是否允许真实 Tavily/外部网络，还是按 case 标记。
5. multi-turn case 是否复用同一个 `conversation_id`，以及如何标记测试运行边界。
6. 失败归因第一版只做规则归因，还是接入 LLM judge。
