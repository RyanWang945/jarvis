# Jarvis 自省式观测评测与自优化入口设计

日期：2026-06-26

## 1. 目标

让用户可以直接对 Jarvis 说：

```text
把刚才的对话记录为评测集，分析其中的问题并优化。
```

Jarvis 能够基于真实对话、trace、日志和运行产物，完成以下闭环：

```text
定位最近 turn
-> 抽取观测摘要
-> 生成 eval candidate
-> 人工确认为正式 eval case
-> 回放评测
-> 分析失败模式
-> 提出优化建议
-> 可选修改代码 / prompt
-> 跑回归验证
```

最终目标是：Jarvis 可以观察自己、评测自己、改进自己，并且所有改进都能通过可重放评测集验证。

## 2. 核心判断

不要把原始日志文件和原始 trace 直接暴露给 LLM。

应暴露结构化自省工具，让 Jarvis 通过业务语义查询自己的运行记录：

- 最近发生了哪些 turn
- 某个 turn 的 trace 摘要是什么
- planner 如何决策
- 调用了哪些 node / tool / LLM
- 哪些地方耗时、失败或产生异常
- 最终回答和用户目标是否匹配

日志和 trace 是底层数据源，不是直接交给模型消费的上下文。

## 3. 建议工具边界

### 3.1 查询最近 turn

能力：

```text
get_recent_turns
```

用途：

- 支持“刚才那轮”“上一轮”“最近失败的任务”等自然语言定位。
- 返回 turn_id、conversation_id、trace_id、用户输入摘要、状态、route、时间、耗时。

### 3.2 查询 turn 观测摘要

能力：

```text
get_turn_observability
```

用途：

- 给定 turn_id 或 trace_id，返回结构化观测摘要。
- 包含 route、plan、node、tool、LLM、token、latency、error、final answer。

### 3.3 从 turn 创建评测候选

能力：

```text
create_eval_candidate_from_turn
```

用途：

- 把真实对话转为候选评测样本。
- 不直接进入正式评测集，先进入候选池。

### 3.4 提升为正式 eval case

能力：

```text
promote_eval_candidate
```

用途：

- 在用户确认或轻标注后，将候选样本提升为正式 eval case。
- 支持 should_route、expected_tools、forbidden_tools、required_status、success_criteria、tags。

### 3.5 回放评测

能力：

```text
run_eval_cases
```

用途：

- 回放单个或多个 eval case。
- 输出结构化评测结果，而不是只有 pass/fail。

### 3.6 失败分析

能力：

```text
analyze_eval_failures
```

用途：

- 聚合失败原因。
- 区分 fast intent、planner、tool、node runtime、aggregation、prompt、权限、格式等问题。

### 3.7 优化建议与修改

能力：

```text
propose_optimization_patch
verify_optimization
```

用途：

- 基于失败分析提出 prompt / runtime / tool 策略修改建议。
- 可选调用 coder 修改代码。
- 修改后必须跑相关 eval 和回归集。

## 4. 交互流程

用户：

```text
把刚才这轮记录为评测集，分析问题并优化。
```

Jarvis 执行：

1. 定位最近 turn。
2. 读取该 turn 的观测摘要。
3. 生成 eval candidate。
4. 展示候选摘要和建议标注。
5. 等用户确认后提升为正式 eval case。
6. 回放当前 case，建立 baseline。
7. 分析失败或薄弱点。
8. 给出优化建议。
9. 如用户同意，修改 prompt / runtime / tool 代码。
10. 重跑当前 case 和相关回归集。
11. 输出 before / after 结果。

## 5. 可重放评测集要求

正式 eval case 不能只保存用户问题。

至少需要保存：

- case_id
- source_conversation_id
- source_turn_id
- source_trace_id
- messages
- 必要 session_state 摘要
- runtime_config 摘要
- available_tools 摘要
- expected_route
- expected_tools
- forbidden_tools
- required_status
- success_criteria
- tags

评测应支持两种模式：

1. 行为回放：重新执行 Jarvis，验证 route、tool、node、final answer。
2. 快照评测：基于历史 trace / raw_payload 做低成本 judge 和失败分析。

## 6. 安全边界

可以自动完成：

- 定位 turn
- 生成 eval candidate
- 抽取观测摘要
- 运行评测
- 聚合失败
- 生成优化建议

需要确认后执行：

- 提升为正式 eval case
- 修改 prompt
- 修改 runtime / tool 代码
- 合入优化结果

任何自动修改都必须经过 eval gate。

## 7. 最小实现路径

### V1：记录与回放

支持：

```text
把刚才这轮记录为评测集
```

能力：

- 定位最近 turn
- 生成 eval candidate
- 用户确认
- 写入 eval fixture / 数据集
- 单 case 回放

### V2：分析与归因

支持：

```text
分析最近失败的评测
```

能力：

- trace-based failure analysis
- 失败类型聚合
- 输出优化建议

### V3：受控自优化

支持：

```text
根据这些失败修改 prompt，并跑回归
```

能力：

- 生成 patch
- 运行目标 eval
- 运行回归 eval
- 输出 before / after
- 通过 gate 后等待人工合入

## 8. 结论

Jarvis 的自优化不应从“自动改代码”开始，而应从“真实对话可沉淀、可回放、可归因”开始。

推荐路径：

```text
自省查询
-> eval candidate
-> reviewed eval case
-> replayable eval
-> failure analysis
-> gated optimization
```

这样 Jarvis 才是在基于真实数据稳定进化，而不是基于单次对话随机调整。
