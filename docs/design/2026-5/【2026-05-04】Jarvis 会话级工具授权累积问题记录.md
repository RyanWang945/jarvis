# Jarvis 会话级工具授权累积问题记录

日期：2026-05-04

## 背景

在使用 Jarvis 让 Codex 修改代码的过程中，用户先要求查看或修改代码，Jarvis 给出计划后，用户回复“好的”。预期行为是：Jarvis 理解这是对上一轮代码任务的确认，并继续把代码修改任务交给 `delegate_to_codex`。

实际日志显示，本轮没有成功暴露 `delegate_to_codex`，模型反复调用 `tool_search` 尝试发现工具，直到达到最大 step 后被迫结束。Codex 并没有真正执行对应代码修改任务。

## 问题现象

典型链路如下：

1. 上一轮用户提出代码相关任务，例如查看或修改 `app/channels/feishu_renderer.py`。
2. Jarvis 返回分析或修改计划。
3. 用户回复“好的”。
4. 新 turn 开始时，Runtime 重新基于当前 turn 做工具裁剪。
5. 当前 human message 只有“好的”，单看不像代码任务。
6. `tool_search` 即使被模型调用，也未能把 `delegate_to_codex` 成功 grant 给本轮。
7. 模型无法调用 Codex，只能继续搜索工具或结束。

这会让“确认后继续执行”的自然多轮工作流断掉。

## 初步根因

当前工具暴露策略更偏向 turn 级别的即时判断：每轮根据当前消息和 runtime policy 重新决定可用工具。

这个策略对明确新任务是合理的，但对“好的 / 继续 / 按这个改 / 可以”这类 continuation message 不够稳，因为当前消息本身没有完整意图。

日志里还暴露出两个具体实现问题：

1. `tool_search` 的授权过滤曾使用最新 human message 做二次判断，导致它看到的是“好的”，而不是模型传入的 `original_user_request`。
2. `tool_search` 对 repo/coding work 的识别偏窄，像 `app/channels/feishu_renderer.py` 这种文件路径不一定会被识别成代码仓库任务。

## 用户建议

用户建议：在同一个 conversation 下，意图识别得到的新工具应该对之前的逻辑做 append，而不是每轮清除。

也就是说，新的工具识别结果应该叠加到 conversation 已有工具上下文中，而不是仅由当前 turn 的一句话完全重算。

## 设计判断

这个方向是对的，但建议不要做成无条件永久 append。

更合理的模型是：conversation 级别维护一个“工具意图上下文”，每个 turn 的新识别结果可以 append 到这个上下文中；当前 turn 的可用工具由以下来源合并得到：

1. runtime policy 的基础工具集合。
2. 当前 turn 明确识别出的工具。
3. conversation 中仍然有效的历史工具意图。
4. continuation message 触发时继承的上一任务工具。

但是需要加上边界，否则会产生过期授权问题。例如用户前面讨论过代码，后面改聊新闻搜索，如果 `delegate_to_codex` 永久留存，模型可能在不该调用时看到过多工具。

## 建议方案

### 1. 引入 conversation-level tool intent state

为 conversation 维护轻量状态，例如：

```json
{
  "active_tool_intents": [
    {
      "tool_name": "delegate_to_codex",
      "source_turn_id": "2446",
      "source_user_request": "查看 app/channels/feishu_renderer.py 文件内容",
      "confidence": "high",
      "expires_after_turns": 3,
      "last_confirmed_at_turn_id": "2447"
    }
  ]
}
```

这个状态不是直接的权限白名单，而是工具意图缓存。真正是否暴露工具，仍要经过 runtime policy、风险规则和当前请求匹配。

### 2. 当前 turn 工具集合采用 append/merge

每一轮工具集合可以按如下方式计算：

```text
allowed_tools_for_turn =
  base_tools_from_runtime_policy
  + tools_detected_from_current_turn
  + valid_tools_from_conversation_intent_state
  + tools_granted_by_tool_search
```

同名工具去重。新识别到的工具 append 到 conversation intent state，不覆盖旧状态。

### 3. continuation message 继承上一任务

如果当前用户消息匹配 continuation intent，例如：

- 好的
- 可以
- 继续
- 按这个改
- 就这么做
- 开始吧
- 执行

则不应只看当前文本，而应回溯最近一条可执行任务意图。若最近任务是 repo/coding work，则本轮应该允许 `delegate_to_codex`。

### 4. 加入过期和清理机制

历史工具意图不应永久有效，建议至少满足以下任一条件时失效：

1. 超过 N 个 turn 未被使用，例如 3 到 5 轮。
2. 用户明确切换主题，例如“换个话题”“不用这个了”“别改代码了”。
3. 当前 turn 识别到互斥强意图，例如从代码修改切到新闻搜索。
4. 工具执行完成且没有后续 pending action。
5. 用户拒绝或取消某个任务。

### 5. `tool_search` 结果应使用 original_user_request 做授权判断

当模型调用 `tool_search` 并传入 `original_user_request` 时，授权过滤应优先使用该字段，而不是只使用最新 human message。

这能解决“好的”这类续接消息丢失原始任务语义的问题。

### 6. repo/coding work 识别应支持路径和文件扩展名

`tool_search` 应识别常见代码路径和文件扩展名，例如：

- `app/channels/feishu_renderer.py`
- `tests/test_xxx.py`
- `pyproject.toml`
- `README.md`
- `*.ts`
- `*.tsx`
- `*.js`
- `*.json`

否则用户自然地说“看下某个文件”时，工具搜索可能无法推荐 `delegate_to_codex`。

## 风险与约束

### 风险 1：工具越积越多

如果 conversation 下所有识别过的工具都一直 append，后续模型可见工具会越来越多，反而增加误调用概率和 token 成本。

应通过 TTL、主题切换检测和任务完成状态清理历史工具意图。

### 风险 2：高风险工具不应仅靠历史意图开放

例如 commit、push、文件修改、外部写入等工具，即使 conversation 中存在历史意图，也仍然需要当前请求或 continuation 语义支撑。

`delegate_to_codex` 可以因“好的”继承上一轮代码计划，但不应因为十轮前讨论过代码就在任意新话题里出现。

### 风险 3：append 不能绕过 runtime policy

conversation-level append 只能作为候选来源，不能绕过 mode routing、approval policy、仓库注册和 commit/push 权限检查。

## 推荐落地顺序

1. 修复 `tool_search` 授权过滤：优先使用 `original_user_request`。
2. 扩展 repo/coding work 识别：支持代码路径和文件扩展名。
3. 增加 continuation intent 判断：当前消息为确认/继续时继承最近任务意图。
4. 引入 conversation-level `active_tool_intents` 状态。
5. 增加 TTL 和主题切换清理。
6. 增加测试覆盖：
   - 用户代码请求后回复“好的”，应暴露 `delegate_to_codex`。
   - 用户切换到新闻搜索后，不应继续暴露过期代码工具。
   - 文件路径请求应被识别为 repo/coding work。
   - 历史工具 append 后应去重。

## 当前结论

“append 而不是清除”的方向是合理的，尤其适合多轮 conversation 中的确认、继续和执行场景。

但 append 应该发生在 conversation 级工具意图状态中，并带有过期、去重、主题切换和风险控制。当前 turn 最终可见工具应该是 runtime policy、当前识别结果、有效历史意图和 `tool_search` grant 的合并结果，而不是简单永久累积所有历史工具。

## 第一版落地

第一版先实现 conversation 级 append，不引入复杂 TTL：

1. conversation metadata 中新增 `active_tool_intents`，保存当前会话识别过的高意图工具名。
2. 每个 turn 初始化时，将 runtime policy 的工具与 `active_tool_intents` 合并并去重。
3. 当前 turn 的 runtime policy 或 `tool_search` 新识别出的高意图工具，会 append 回 `active_tool_intents`。
4. `command` 和 `image_generation` turn 不合并历史工具，避免历史工具绕过禁用工具的 runtime policy。
5. 同时补充代码路径识别，避免 `app/channels/feishu_renderer.py` 这类请求无法触发 `delegate_to_codex` 候选。

后续仍建议补 TTL、主题切换清理和 source turn 记录。
