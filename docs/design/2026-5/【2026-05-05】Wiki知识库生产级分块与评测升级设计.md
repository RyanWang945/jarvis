# Wiki 知识库生产级分块与评测升级设计

## 1. 背景

当前 wiki 知识库已经具备基础 ingestion、chunk、embedding、OpenSearch 索引、BM25/vector/hybrid/RRF/rerank 检索和离线评测能力。现有默认 wiki 分块 profile 是 `medium_overlap_v1`：

```text
target_size = 800
soft_min_size = 500
hard_max_size = 1200
overlap_size = 120
```

当前实现位于 `app/knowledge_base/chunking.py`，本质是：

```text
normalize text
-> 按段落和句子切分
-> 按字符数聚合
-> 固定字符 overlap
```

这套策略适合作为 MVP，但离生产级 RAG/检索系统还有几个关键差距：

- chunk 没有稳定携带标题、章节、层级上下文。
- `section_path` 对 wiki 基本为空。
- `chunk_id` 当前没有包含 `chunk_profile_id`，多分块策略不能安全并存。
- eval dataset 的 gold 绑定 `target_chunk_id`，换分块策略后无法公平评测。
- reranker 已证明离线质量有效，但本地单服务在 5 QPS 下无法承受大候选量，需要预算化调用。

本设计目标是把 wiki 知识库升级成：

```text
可多分块策略并存
可稳定重建索引
可跨分块策略公平评测
可生产化观测和回滚
```

## 2. 借鉴的开源与生产经验

### 2.1 分块应保留自然结构

LangChain 文档建议优先使用保留自然文本结构的 splitter，例如递归地尽量保留段落、句子等较大语义单元，再控制 chunk size。这和当前按段落/句子再聚合的方向一致，但我们需要进一步引入标题、章节和 metadata。

Haystack 的 `DocumentSplitter` 支持按 word/sentence/passage/page/line/function 等单位切分，并保留 overlap、source_id、page_number 以及原文 metadata。这说明生产索引中的 chunk 不应只是文本片段，还应保留可追溯 metadata。

### 2.2 chunk 是带 metadata 和关系的节点

LlamaIndex 把 chunk 抽象为 Node，Node 可以继承 Document metadata，也可以显式记录前后节点、父节点等 relationship。这个设计对 wiki 很重要：wiki chunk 应该知道自己来自哪个词条、哪个章节、相邻 chunk、父级 section。

LlamaIndex 还提供 metadata extraction、title/keyword/entity/summary 等上下文增强思路。对我们的 wiki 场景，第一步不需要复杂 LLM metadata extraction，至少要做 deterministic 的标题和章节路径注入。

### 2.3 小粒度检索、大上下文使用

LlamaIndex 的 sentence-window 思路是：检索可以用较小粒度节点，但交给 LLM 时替换成包含相邻句子的窗口上下文。这个经验可以转化为我们的两类字段：

```text
body_content      # 原始正文，用于展示和 span 定位
retrieval_content # 注入标题/章节后的检索文本
rerank_content    # 控制长度、面向 cross-encoder 的精排文本
answer_content    # 回答阶段可扩展窗口上下文
```

### 2.4 检索评测需要稳定 gold，而不是绑定当前 chunk

LlamaIndex retrieval eval 使用 expected ids、hit-rate、MRR 等指标；Haystack 有 DocumentRecallEvaluator、MRR、mAP 等统计评测；Ragas 提供 context precision/context recall/faithfulness 等 RAG 指标。

这些实践说明：

- 检索评测需要明确 ground truth。
- 多个正确证据是常态，不应只支持单一 chunk id。
- 生成质量还需要 context recall、faithfulness 等 RAG 层指标。

对“比较不同分块策略”而言，`chunk_id` 不是稳定 ground truth。生产级 gold 应该绑定文档内证据范围，即 evidence span。

### 2.5 混合检索和 rerank 是两阶段链路

OpenSearch 官方 hybrid search 通过 pipeline 对多路 query 分数做 normalization/combination，也支持 rank-based score ranker。OpenSearch rerank processor 在搜索响应阶段对结果重新排序，且文档指出 rerank 会在 normalization 后改变最终排序。

这和我们的链路一致：

```text
BM25 + Vector
-> RRF / hybrid fusion
-> rerank
-> final top_k
```

生产设计上必须把 recall candidate、fusion、rerank 分阶段记录，避免只看最终结果而不知道问题出在哪一层。

## 3. 目标架构

目标 wiki 知识库链路：

```text
Raw Wiki Source
  -> Document Normalization
  -> Structure Parser
  -> Chunk Profile Runner
  -> Chunk Store
  -> Embedding Store
  -> OpenSearch Index per Profile
  -> Retrieval Pipeline
  -> Eval Pipeline
  -> Observability
```

核心原则：

1. **Document 稳定，Chunk 可变**  
   document 是长期稳定实体，chunk 是某个 chunk profile 的派生产物。

2. **Gold 绑定 evidence span，不绑定 chunk id**  
   同一批 query 可以公平评测不同 chunk profile。

3. **Profile 并存，索引隔离**  
   新旧分块策略同时存在，按 profile 单独索引、单独评测、可回滚。

4. **检索分层，rerank 预算化**  
   RRF 是稳定主链路，reranker 是受预算控制的精排插件。

## 4. 分块升级设计

### 4.1 新 profile

新增 wiki profile：

```text
chunk_profile_id = wiki_heading_context_v2
name = Wiki Heading Context V2
language = zh
chunker_version = wiki_heading_context_v2
target_size = 900
soft_min_size = 500
hard_max_size = 1300
overlap_size = 120
```

`boundary_rules_json`：

```json
{
  "mode": "heading_aware",
  "split_units": ["section", "paragraph", "sentence"],
  "inject_document_title": true,
  "inject_section_path": true,
  "preserve_section_boundary": true,
  "section_change_resets_overlap": true
}
```

`normalization_rules_json`：

```json
{
  "retrieval_prefix_template": "标题：{title}\\n章节：{section_path}\\n\\n",
  "rerank_max_chars": 1800,
  "answer_window_prev_chunks": 1,
  "answer_window_next_chunks": 1
}
```

### 4.2 wiki 结构解析

当前 wiki record 主要是：

```json
{
  "id": "...",
  "url": "...",
  "title": "...",
  "text": "..."
}
```

如果源数据只有 plain text，则 v2 至少做 title injection：

```text
标题：数学

正文...
```

如果源数据能保留或恢复章节结构，则解析成：

```json
{
  "title": "数学",
  "sections": [
    {
      "section_path": ["历史"],
      "text": "..."
    },
    {
      "section_path": ["应用", "科学"],
      "text": "..."
    }
  ]
}
```

优先级：

1. 支持已有 structured sections。
2. 支持从 wiki markdown/mediawiki heading 解析 section。
3. 没有 heading 时退化为 title-only context。

### 4.3 chunk 字段语义

短期复用现有 `kb_chunks` 字段：

| 字段 | v2 语义 |
| --- | --- |
| `raw_content` | 不带标题/章节注入的正文 |
| `normalized_content` | 用于 embedding/BM25 的标题+章节+正文 |
| `section_path` | 章节路径字符串 |
| `metadata_json.body_content` | 原始正文备份 |
| `metadata_json.document_title` | 文档标题 |
| `metadata_json.section_title` | 当前章节标题 |
| `metadata_json.context_prefix` | 注入前缀 |
| `metadata_json.rerank_content` | 控长后的 reranker 文本 |
| `metadata_json.char_span_source` | char span 基于原文还是 normalized text |

长期建议 schema 显式化：

```text
body_content TEXT
retrieval_content TEXT
rerank_content TEXT
answer_content TEXT
```

这样可以避免 `normalized_content` 语义过载。

### 4.4 chunk id 必须升级

当前 wiki chunk id：

```text
{doc_id}:chunk:{chunk_index:04d}
```

问题：没有包含 `chunk_profile_id`。同一 document 用不同 profile 重新分块时，`chunk_id` 主键冲突，旧 chunk 会被覆盖。

新规则：

```text
{doc_id}:profile:{chunk_profile_id}:chunk:{chunk_index:04d}
```

示例：

```text
wikipedia_zh_real_300:13:profile:wiki_heading_context_v2:chunk:0000
```

兼容策略：

- 旧 profile 的旧 chunk id 保留，不强制迁移。
- 新 profile 一律使用新 chunk id。
- 新代码不得从 chunk id 字符串推断 profile，必须读字段。

### 4.5 parent-child / window 上下文

v2 先不引入复杂 parent-child 表，但 metadata 要预留：

```json
{
  "prev_chunk_id": "...",
  "next_chunk_id": "...",
  "parent_section_id": "...",
  "section_path": ["应用", "科学"]
}
```

回答阶段可以按 `prev_chunk_id/next_chunk_id` 扩展上下文，实现“检索小 chunk，回答大窗口”。

## 5. 评测体系升级

### 5.1 当前问题

当前 `kb_eval_queries`：

```text
doc_id
target_chunk_id
query_text
gold_answer
gold_evidence_json
```

`run_evaluation()` 当前主要判断：

```python
hit_rank = _find_hit_rank(search_hits, target_chunk_id)
```

这使 eval dataset 与某个 chunk profile 强绑定。换分块策略后：

- chunk id 变化。
- chunk 边界变化。
- 旧 target chunk 可能被拆分或合并。
- 直接复用旧 dataset 会把相关结果算 miss。

### 5.2 生产级 gold：Evidence Span

生产级评测数据应基于稳定 evidence span：

```json
{
  "doc_id": "wikipedia_zh_real_300:106",
  "char_start": 1200,
  "char_end": 1850,
  "evidence_text": "...",
  "evidence_hash": "...",
  "source_profile": "medium_overlap_v1",
  "source_chunk_id": "wikipedia_zh_real_300:106:chunk:0000"
}
```

query 生成应该基于 evidence span，而不是基于 chunk id：

```text
从文档中选择一段事实证据
-> 记录 doc_id + char_start + char_end
-> 基于证据生成 query
-> 用同一个 query/span 评测不同 chunk profile
```

### 5.3 命中规则

跨分块策略评测时，retrieved chunk 命中 gold span 的规则：

```text
overlap = intersection(retrieved_chunk_span, gold_span)
gold_coverage = overlap_chars / gold_span_chars
chunk_precision = overlap_chars / retrieved_chunk_chars
```

建议默认 hit 条件：

```text
overlap_chars >= 80
AND gold_coverage >= 0.30
```

对于短事实句：

```text
gold_span_chars < 160 时，overlap_chars >= 40 即可
```

需要同时记录：

- `span_hit@k`
- `doc_hit@k`
- `chunk_id_hit@k`
- `coverage_ratio`
- `noise_ratio = 1 - chunk_precision`

### 5.4 多 gold 支持

一个 query 可以有多个正确证据：

```json
[
  {
    "doc_id": "...",
    "char_start": 1200,
    "char_end": 1850
  },
  {
    "doc_id": "...",
    "char_start": 3200,
    "char_end": 3500
  }
]
```

命中任一 evidence 即算 hit；MRR 使用第一个命中 evidence 的排名。

### 5.5 可复用评测机制

后续评测机制不应只服务 wiki 分块实验，而应成为知识库统一评测底座，能复用到：

- wiki
- SEC filing
- deep research / business corpus
- 未来 Obsidian 或其他结构化知识源

可复用评测机制需要把四件事解耦：

```text
Dataset: 固定问题、答案、证据 gold
Retriever: 某个检索配置或 pipeline
Judge: 命中规则和指标计算
Report: 聚合、对比和回归阈值
```

也就是说，同一个 dataset 可以被多个 retriever/profile 复用；同一个 retriever 可以被多个 dataset 评测；同一个 judge 可以在 wiki、SEC、业务文档上复用。

#### 5.5.1 Dataset 抽象

Dataset 必须表达稳定任务，而不是表达某次索引实现。

```json
{
  "dataset_id": "wiki_200q_span_v1",
  "corpus_id": "wikipedia_zh_real_300",
  "dataset_type": "retrieval_span",
  "generation_method": "llm",
  "query_model": "deepseek-v4-flash",
  "schema_version": "span_v1",
  "items": [
    {
      "query_id": "...",
      "query_text": "开源操作系统内核是谁发起的",
      "query_type": "fact",
      "difficulty": "medium",
      "gold_answer": "Linus Torvalds",
      "evidence": [
        {
          "doc_id": "wikipedia_zh_real_300:...",
          "char_start": 1200,
          "char_end": 1450,
          "evidence_text": "...",
          "evidence_hash": "..."
        }
      ]
    }
  ]
}
```

Dataset 不应包含：

- 当前 OpenSearch index name。
- 当前 chunk profile 的 chunk id 作为唯一 gold。
- 当前 reranker 配置。

这些属于 run config。

#### 5.5.2 Evidence 类型

为了跨语料复用，gold evidence 需要支持多种类型。

| Evidence 类型 | 适用语料 | 命中方式 |
| --- | --- | --- |
| `span` | wiki、普通长文 | `doc_id + char_start/char_end` overlap |
| `section` | SEC、结构化文档 | `doc_id + section_path` 或 section id |
| `page_span` | PDF/财报 | `doc_id + page_number + char span/bbox` |
| `document` | 粗粒度问答 | 只要求命中 doc |
| `chunk_legacy` | 旧评测兼容 | chunk id 精确匹配 |

第一版先实现 `span` 和 `chunk_legacy`。SEC 以后可以扩展 `section/page_span`，不需要推翻评测框架。

#### 5.5.3 Retriever Run Config

每次评测 run 要完整记录检索配置：

```json
{
  "retrieval_mode": "rrf_v2_rerank",
  "chunk_profile_id": "wiki_heading_context_v2",
  "index_name": "kb_wikipedia_zh_wiki_heading_context_v2",
  "top_k": 5,
  "params": {
    "bm25_candidate_k": 50,
    "vector_candidate_k": 50,
    "rrf_k": 60,
    "rerank_input_top_k": 50,
    "rerank_model": "bge-reranker-v2-m3",
    "rerank_timeout_ms": 3000,
    "span_hit_policy": "overlap_v1"
  }
}
```

这样报告才能回答：

- 是哪个 chunk profile 赢了？
- 是哪个 retrieval mode 赢了？
- 是候选池变宽带来的收益，还是 reranker 带来的收益？
- 质量提升是否伴随延迟不可接受？

#### 5.5.4 Judge / Metrics 抽象

Judge 接收：

```text
query item
retrieved hits
hit policy
```

输出单 query 级别指标：

```json
{
  "query_id": "...",
  "chunk_id_hit": false,
  "span_hit": true,
  "doc_hit": true,
  "hit_rank": 2,
  "mrr": 0.5,
  "ndcg": 0.6309,
  "coverage_ratio": 0.72,
  "noise_ratio": 0.41,
  "matched_evidence_id": "...",
  "matched_chunk_id": "...",
  "latency_ms": 123
}
```

聚合指标：

- `span_hit@k`
- `doc_hit@k`
- `chunk_id_hit@k`
- `MRR`
- `nDCG`
- `coverage_ratio_avg`
- `noise_ratio_avg`
- `avg/p50/p95/p99 latency`
- `fallback_rate`

第一版必须同时保留旧 `chunk_id_hit`，用于确认新 span judge 没有明显偏离旧评测。

#### 5.5.5 Report 抽象

评测报告应该固定输出对比矩阵：

| dataset | chunk_profile | retrieval_mode | top_k | span_hit@k | doc_hit@k | MRR | nDCG | avg latency | p95 latency |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |

并要求每个实验至少包含一个 baseline：

- 分块实验 baseline：`medium_overlap_v1 + rrf_v2`
- rerank 实验 baseline：`same profile + rrf_wide_no_rerank`
- 并发实验 baseline：串行同配置结果

没有 baseline 的单点指标不能作为上线依据。

### 5.6 Eval schema 升级

短期方案：复用 `gold_evidence_json` 存 span，同时保留 `target_chunk_id` 兼容旧逻辑。

示例：

```json
{
  "version": "span_v1",
  "evidence": [
    {
      "doc_id": "wikipedia_zh_real_300:106",
      "char_start": 1200,
      "char_end": 1850,
      "evidence_hash": "...",
      "source_chunk_id": "..."
    }
  ]
}
```

长期方案：新增表。

```sql
CREATE TABLE kb_eval_evidence_spans (
    evidence_id TEXT PRIMARY KEY,
    query_id TEXT NOT NULL,
    doc_id TEXT NOT NULL,
    char_start INTEGER NOT NULL,
    char_end INTEGER NOT NULL,
    evidence_text TEXT,
    evidence_hash TEXT,
    source_chunk_profile_id TEXT,
    source_chunk_id TEXT,
    metadata_json TEXT,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

并扩展 results：

```sql
ALTER TABLE kb_eval_results ADD COLUMN doc_hit INTEGER;
ALTER TABLE kb_eval_results ADD COLUMN span_hit INTEGER;
ALTER TABLE kb_eval_results ADD COLUMN span_hit_rank INTEGER;
ALTER TABLE kb_eval_results ADD COLUMN coverage_ratio REAL;
ALTER TABLE kb_eval_results ADD COLUMN noise_ratio REAL;
```

### 5.7 同一 dataset 如何评测不同分块策略

使用 span-based dataset 后，同一 dataset 可直接用于多个 profile：

```text
dataset_id = wiki_200q_span_v1
run A: chunk_profile_id = medium_overlap_v1
run B: chunk_profile_id = wiki_heading_context_v2
run C: chunk_profile_id = wiki_semantic_v3
```

每次 run 动态判断 retrieved chunks 是否覆盖 gold span。

短期如果不改 evaluator，则做派生 dataset：

```text
wiki_200q_base
wiki_200q_medium_overlap_v1
wiki_200q_wiki_heading_context_v2
```

派生规则：

```text
gold span -> 当前 profile 下 overlap 最大 chunk -> target_chunk_id
```

但这只是过渡方案。最终应使用 span hit 作为跨 profile 主指标。

### 5.8 评测代码结构建议

当前 `KnowledgeBaseEvaluationService` 同时负责 dataset、检索、指标计算和结果写入。为了可复用，建议逐步拆成：

```text
EvalDatasetRepository
  - load dataset / queries / evidence

EvidenceResolver
  - parse gold_evidence_json
  - legacy chunk -> span migration
  - multi evidence handling

RetrievalRunner
  - run bm25/vector/hybrid/rrf/rerank
  - return SearchHit with doc/chunk/span metadata

EvalJudge
  - chunk_id_hit
  - span_overlap_hit
  - doc_hit
  - MRR/nDCG/coverage/noise

EvalReporter
  - aggregate
  - compare baselines
  - write markdown/json report
```

第一步不必拆文件，但实现时应按这些函数边界组织，避免后续 SEC/业务知识库复用时再重写一套 evaluator。

### 5.9 Dataset 生命周期

可复用 dataset 要有生命周期状态：

```text
generated -> reviewed -> frozen -> deprecated
```

上线比较必须使用 `frozen` dataset。原因：

- `generated` dataset 可能有错误 gold。
- `reviewed` dataset 经过人工抽查但仍可修改。
- `frozen` dataset 不再修改 query/evidence，只允许新增 run。
- `deprecated` dataset 只保留历史结果，不再作为回归门禁。

当前 `review_status` 在 query 级别已经存在，可以继续使用；dataset 级别建议后续增加 `status` 或写入 `metadata_json`。

### 5.10 回归门禁

生产级评测不仅用于实验，还应作为回归门禁。

建议第一版门禁：

```text
span_hit@5 不低于 baseline - 0.01
MRR 不低于 baseline - 0.02
doc_hit@5 不低于 baseline
p95 latency 不高于 baseline * 1.5
fallback_rate 不高于 5%
```

分块策略实验可以放宽 latency；默认线上配置不能放宽 fallback 和 p95 latency。

## 6. 检索链路升级

### 6.1 标准链路

```text
BM25 candidate_k
Vector candidate_k
-> RRF fusion
-> optional rerank
-> final top_k
```

每个 profile 单独建索引：

```text
kb_wikipedia_zh_medium_overlap_v1
kb_wikipedia_zh_wiki_heading_context_v2
```

检索结果必须返回：

```json
{
  "chunk_id": "...",
  "doc_id": "...",
  "chunk_profile_id": "...",
  "char_start": 1200,
  "char_end": 1850,
  "section_path": "...",
  "retrieval_score": 0.1,
  "reranker_score": 6.5
}
```

### 6.2 Reranker 预算化

本地 reranker 服务已验证：

- 串行 `input50` 质量好。
- 5 QPS 下 `input50` 基本不可用。

因此架构上必须把 reranker 作为稀缺资源：

```text
RerankBudgetManager
  - max_concurrency
  - max_queue_size
  - timeout/deadline
  - circuit_breaker
  - adaptive_input_k
```

建议策略：

| 模式 | 候选 | 使用场景 |
| --- | ---: | --- |
| `fast` | 不 rerank | 默认低延迟 |
| `balanced` | RRF 20/30 -> rerank | 日常高质量 |
| `quality` | RRF 50 -> rerank | 明确高质量、低并发 |
| `degraded` | RRF only | reranker 忙、超时或熔断 |

## 9. 验收标准

### 数据正确性

- 同一 document 可同时存在至少两个 chunk profile。
- 新旧 profile 的 embedding 不冲突。
- 新旧 profile 的 OpenSearch index 可独立重建和删除。
- eval dataset 可在不同 profile 下运行，不依赖固定 chunk id。

### 检索质量

- `wiki_heading_context_v2` 的 `span_hit@5` 不低于 `medium_overlap_v1`。
- `doc_hit@5` 不低于旧 profile。
- rerank 模式下 MRR/nDCG 有显著提升。
- `noise_ratio` 不显著恶化。

### 线上稳定性

- 默认模式不依赖 reranker。
- reranker 超时不影响 RRF 返回。
- reranker fallback rate 可观测。
- `/health` 不应被 rerank 推理请求拖死。

## 10. 风险与取舍

### 风险 1：标题注入导致噪声

标题注入可能让所有 chunk 都更容易命中文档标题型 query，但也可能稀释正文相关性。

缓解：

- `body_content` 和 `retrieval_content` 分离。
- 对 BM25/title/content 使用不同 boost。
- rerank 使用控长 `rerank_content`。

### 风险 2：span hit 阈值影响指标

span overlap 阈值太松会虚高，太严会误杀。

缓解：

- 同时报 `span_hit/doc_hit/chunk_hit`。
- 报 `coverage_ratio/noise_ratio`。
- 固定阈值并写入 eval run params。

### 风险 3：多 profile 存储成本增加

多 profile 意味着更多 chunks、embeddings、OpenSearch index。

缓解：

- profile 有生命周期。
- 只保留 active profile 和 last-good profile。
- embedding 生成和索引重建走 batch job。

## 11. 结论

wiki 知识库要进入生产级，核心不是简单把 chunk 切得更细或更大，而是把体系升级为：

```text
稳定文档
可版本化 chunk profile
标题/章节上下文增强
profile-independent span gold
跨 profile 同题评测
RRF 保底 + rerank 预算化精排
完整观测和回滚
```

最优先的两个基础改造是：

1. 修复 chunk id，使不同分块 profile 可以安全并存。
2. 把评测 gold 从 `target_chunk_id` 升级到 evidence span。

这两点完成后，wiki 分块策略才能被持续实验、对比和迭代，而不是每次重分块都让旧评测集失效。
