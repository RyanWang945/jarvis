---

## 1. 结论

Jarvis 需要引入三个核心概念：

1. `Repository Registry`：Jarvis 已知的本地仓库资源。
2. `Repository Grant`：某个主体对某个仓库拥有的授权关系。
3. `Approval Request`：所有人工审批的业务事实源。

核心原则：

- Jarvis 控制的是仓库资源，不是任意本地路径。
- `repositories` 记录资源是什么；`repository_grants` 记录谁拥有什么权限；`approval_requests` 记录权限或动作审批从哪里来。
- LLM 不应自由传绝对 `workdir`；目标形态是只传 `repo_id`。
- 所有本地资源工具执行前必须经过 `RepositoryRegistry + ToolGate`。
- 审批链路不依赖 LangGraph interrupt；interrupt 只是未来可选实现机制。
- 第一版采用“turn A 创建审批并停止，用户批准后 turn B 消费审批结果”的模型。

目标链路：

```text
User request
  -> Runtime policy
  -> Need repo access?
       -> yes: create approval_request(type=repo_access), stop current turn
       -> no: resolve repo_id
  -> ToolGate checks repository grant + capability + path boundary
  -> delegate_to_codex(repo_id=jarvis, ...)
  -> ToolExecutionResult
```

设计优先级：

1. 先立住执行级 Tool Gate，防止工具绕过授权。
2. 再补审批体验和飞书卡片。
3. 最后再考虑 LangGraph interrupt/checkpoint。

## 2. 当前问题

### 2.1 workdir 过于自由

当前 coder 工具参数包含：

```text
workdir: Absolute path to the target repository working directory.
```

问题：

- LLM 可以构造任意绝对路径。
- Jarvis 没有长期事实源记录哪些目录被授权。
- 工具层只能检查 `Path(workdir).exists()`，无法判断用户是否批准过该目录。
- Jarvis 修改自己和修改外部仓库没有权限模型上的区别。
- 多仓库审计只能看到路径，看不到资源身份、授权主体和授权来源。

### 2.2 审批链路没有业务事实源

历史设计提到过 `permission_requests` 和 LangGraph interrupt，但当前实现还没有完整审批链路。

审批不应直接依赖 LangGraph interrupt：

- 审批是业务事实，不是图节点临时状态。
- 当前 runtime 是同步 ReAct loop，还没有稳定 checkpoint/resume。
- 飞书、API、CLI 都需要共用同一审批状态。
- 审批可能很久以后才发生，原 turn 上下文可能已经过期。
- 审批消费、失败、幂等和过期都需要独立状态机。

## 3. 数据模型

### 3.1 repositories

`repositories` 表记录 Jarvis 已知的本地仓库资源。它描述“资源是什么”，不直接等价于“当前主体有权限”。

建议字段：

```sql
CREATE TABLE jarvis.repositories (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    repo_uid CHAR(36) NOT NULL UNIQUE,
    repo_id VARCHAR(128) NOT NULL UNIQUE,
    name VARCHAR(255) NOT NULL,
    root_path VARCHAR(1024) NOT NULL,
    canonical_root_path VARCHAR(1024) NOT NULL,
    path_hash CHAR(64) NOT NULL UNIQUE,
    status VARCHAR(32) NOT NULL,
    owner_user_id VARCHAR(128),
    created_by VARCHAR(128),
    source_approval_id VARCHAR(128),
    last_verified_at DATETIME(6),
    metadata JSON,
    notes TEXT,
    created_at DATETIME(6) NOT NULL,
    updated_at DATETIME(6) NOT NULL,
    UNIQUE KEY uk_repositories_canonical_root_path (canonical_root_path),
    KEY idx_repositories_status (status),
    KEY idx_repositories_owner (owner_user_id)
);
```

状态：

```text
pending
active
disabled
revoked
```

字段说明：

- `repo_uid`：内部稳定 ID，避免人类可读 `repo_id` 重命名影响审计。
- `repo_id`：工具可使用的人类友好别名，由后端规范化生成。
- `root_path`：展示用原始路径。
- `canonical_root_path`：标准化路径，用于比较和执行。
- `path_hash`：标准化路径 hash，避免 Windows 大小写、斜杠差异导致重复注册。
- `source_approval_id`：首次注册来源审批。
- `last_verified_at`：最近一次确认路径仍存在且满足 repo root policy。

Jarvis 自己应默认注册：

```text
repo_id = jarvis
name = Jarvis
root_path = E:\pythonProject\jarvis
canonical_root_path = E:\pythonProject\jarvis
status = active
```

### 3.2 repository_grants

`repository_grants` 表记录某个主体对某个仓库的授权。它描述“谁拥有什么权限”。

第一版如果只面向单用户，可以暂缓落表，把 grant 字段折叠到 `repositories`；但设计上必须承认资源和授权关系是两件事。

建议字段：

```sql
CREATE TABLE jarvis.repository_grants (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    repo_uid CHAR(36) NOT NULL,
    subject_type VARCHAR(32) NOT NULL,
    subject_id VARCHAR(128) NOT NULL,
    permission_level VARCHAR(32) NOT NULL,
    capabilities JSON,
    allowed_tools JSON,
    source_approval_id VARCHAR(128),
    status VARCHAR(32) NOT NULL,
    expires_at DATETIME(6),
    created_at DATETIME(6) NOT NULL,
    updated_at DATETIME(6) NOT NULL,
    UNIQUE KEY uk_repo_subject_permission (repo_uid, subject_type, subject_id, permission_level),
    KEY idx_repository_grants_subject (subject_type, subject_id),
    KEY idx_repository_grants_status (status)
);
```

主体类型：

```text
user
conversation
system
```

grant 状态：

```text
active
revoked
expired
```

权限级别：

```text
read
write
coder
admin
```

权限级别只是粗粒度分层，执行时还要检查 capability。

建议 capability：

```text
read_files
search_files
write_files
run_tests
run_safe_shell
delegate_to_codex
git_commit
git_push
network_access
read_secrets
```

第一版映射：

```text
read:
  - read_files
  - search_files

write:
  - read_files
  - search_files
  - write_files

coder:
  - read_files
  - search_files
  - write_files
  - run_tests
  - run_safe_shell
  - delegate_to_codex
```

必须单次审批：

```text
git_push
destructive_shell
secret_file_read
network_exfiltration_risk
```

`allowed_tools` 不应只记录工具名，建议包含工具内限制：

```json
{
  "delegate_to_codex": {
    "allowed": true,
    "allow_commit": false,
    "allow_push": false,
    "allow_network": false
  },
  "shell_run_command": {
    "allowed": true,
    "mode": "safe_only"
  }
}
```

### 3.3 approval_requests

`approval_requests` 表记录所有需要用户决定的审批。

建议字段：

```sql
CREATE TABLE jarvis.approval_requests (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    approval_id VARCHAR(128) NOT NULL UNIQUE,
    conversation_id BIGINT NOT NULL,
    turn_id BIGINT,
    requester_message_id BIGINT,
    type VARCHAR(64) NOT NULL,
    status VARCHAR(32) NOT NULL,
    risk_level VARCHAR(32) NOT NULL,
    idempotency_key VARCHAR(128),
    requested_scope JSON NOT NULL,
    requested_action JSON NOT NULL,
    resume_payload JSON,
    reason TEXT,
    expires_at DATETIME(6),
    decided_at DATETIME(6),
    decided_by VARCHAR(128),
    decision_reason TEXT,
    decision_message_id BIGINT,
    consume_turn_id BIGINT,
    consumed_at DATETIME(6),
    applied_at DATETIME(6),
    failed_at DATETIME(6),
    last_error TEXT,
    created_at DATETIME(6) NOT NULL,
    updated_at DATETIME(6) NOT NULL,
    UNIQUE KEY uk_approval_idempotency (idempotency_key),
    KEY idx_approval_requests_conversation_status (conversation_id, status),
    KEY idx_approval_requests_turn (turn_id),
    KEY idx_approval_requests_type_status (type, status)
);
```

审批类型：

```text
repo_access
tool_permission
git_push
file_write
shell_command
destructive_operation
secret_file_read
```

审批状态：

```text
pending
approved
rejected
expired
applying
applied
consuming
consumed
failed
cancelled
```

状态流：

```text
repo_access/tool_permission:
  pending -> approved -> applying -> applied | failed

git_push/destructive_operation/shell_command:
  pending -> approved -> consuming -> consumed | failed
```

说明：

- 长期授权审批成功后进入 `applied`，并创建 repository/grant。
- 一次性动作审批成功后进入 `consumed`。
- 危险动作失败后不自动回到 `approved`，避免重复执行。
- `last_error` 记录 apply/consume 失败原因。
- `idempotency_key` 防止同一用户请求重复创建多个相同审批。

`resume_payload` 保存新 turn 消费审批时需要的上下文：

```json
{
  "original_user_intent": "修改 G:\\project-a 的代码",
  "pending_tool_name": "delegate_to_codex",
  "pending_tool_args": {
    "repo_id": "project-a",
    "instruction": "..."
  },
  "conversation_summary": "...",
  "created_from_turn_id": 123
}
```

## 4. Repo Root Policy

`repo_access` approve 不能盲目信任 `approval_requests.requested_scope.path`。该 path 可能来自用户输入、LLM 推断或工具中间结果。批准时必须重新标准化和校验。

### 4.1 Canonicalization

注册仓库前必须执行：

```text
canonicalize_path(path)
check_path_exists(path)
check_path_is_directory(path)
normalize_windows_case_and_drive(path)
resolve_symlink_or_reject(path)
compute_path_hash(canonical_path)
```

Windows 下第一版建议保守处理：

- 盘符大小写标准化。
- UNC path 默认拒绝。
- NTFS junction 默认拒绝。
- subst drive 默认拒绝。
- 8.3 short path 默认拒绝。
- 路径末尾空格或点默认拒绝。

Git 场景也要注意：

- submodule 指向外部路径。
- git worktree。
- repo 内 symlink 指向 repo 外。

第一版不要支持复杂情况，直接保守拒绝。

### 4.2 可授权路径

默认允许：

- 具体 git 仓库根目录。
- 当前 Jarvis 仓库根目录。

默认拒绝：

- 磁盘根目录，例如 `C:\`、`D:\`。
- 用户主目录，例如 `C:\Users\<user>`。
- 系统目录，例如 `C:\Windows`、`C:\Program Files`。
- 父级聚合目录，例如 `E:\pythonProject`。
- `.git` 目录本身。
- repo 内 symlink/junction 指向的外部目录。
- 非 git repo，除非用户通过受信 admin API 手动注册。

批准 repo access 时后端流程：

```text
canonicalize_path(path)
validate_repo_root_policy(canonical_path)
generate_or_validate_repo_id(suggested_repo_id)
create repository
create repository_grant
mark approval applied
```

### 4.3 repo_id 策略

`repo_id` 是人类友好别名，不是不可变主键。

规则：

- 内部外键使用 `repo_uid` 或 bigint id。
- `repo_id` 由后端规范化生成。
- LLM 只能建议 `suggested_repo_id`，不能让它自动生效。
- 规范化包括 lowercase、slugify、去除特殊字符。
- 冲突时加后缀。
- 审计记录同时保存 `repo_uid` 和当时的 `repo_id`。

## 5. 工具参数设计

### 5.1 目标形态

高权限工具不再接收裸 `workdir`，而是接收：

```json
{
  "repo_id": "jarvis",
  "instruction": "...",
  "verification_cmd": "uv run pytest -q",
  "allow_commit": false,
  "allow_push": false
}
```

Jarvis 内部执行：

```text
repo = RepositoryRegistry.resolve(repo_id)
grant = RepositoryGrant.resolve(subject, repo)
ToolGate.check(repo, grant, tool=delegate_to_codex, required_capability=delegate_to_codex)
workdir = repo.canonical_root_path
```

### 5.2 兼容过渡

当前 `delegate_to_codex` 已经使用 `workdir`。迁移时分两步：

第一阶段 schema 同时支持：

```text
repo_id?: string
workdir?: string
```

规则：

- 有 `repo_id`：优先通过 registry 解析 root_path。
- 只有 `workdir`：必须匹配某个 active repository 的 root_path，否则拒绝。
- `repo_id` 和 `workdir` 同时存在：必须指向同一个 root_path，否则拒绝。
- 未授权路径不执行工具，只创建审批请求或返回需要审批。
- 兼容期内如果使用 `workdir`，tool result 必须产生 deprecation warning。

第二阶段移除 `workdir`：

```text
delegate_to_codex(repo_id, instruction, ...)
```

## 6. Tool Gate

Tool Gate 是所有本地资源工具执行前的强制入口。审批系统只是赋予或确认权限，不能替代执行前校验。

### 6.1 强制入口

所有会访问本地资源的工具必须调用：

```python
ToolGate.authorize(
    subject=RuntimeSubject(...),
    tool_name="delegate_to_codex",
    repo_id="jarvis",
    operation=ToolOperation(...),
)
```

返回：

```python
ToolAuthorization(
    allowed=True,
    repo=RepositoryRef(...),
    grant=RepositoryGrantRef(...),
    warnings=[],
)
```

拒绝时：

```python
ToolAuthorization(
    allowed=False,
    reason="repo_id is not authorized",
    approval_request_id="approval_xxx" | None,
)
```

### 6.2 capability 校验

工具到 capability 的最小映射：

```text
shell_inspect -> read_files/search_files
write_file -> write_files
delegate_to_codex -> delegate_to_codex/write_files/run_tests/run_safe_shell
git commit -> git_commit
git push -> git_push + per-action approval
```

repo 有 `coder` grant 不等于允许所有动作：

- `allow_commit=true` 需要 `git_commit` capability。
- `allow_push=true` 必须单次审批，即使有 `coder` grant。
- secret 文件读取必须单次审批或默认拒绝。
- destructive shell 必须单次审批。

### 6.3 deterministic shell guard

shell 风险判断不能只靠 LLM。必须先有确定性 allowlist/blocklist。

默认允许的只读或低风险命令示例：

```text
pwd
ls / dir
cat / type
rg
git status
git diff
git log
git branch
git rev-parse
pytest
uv run pytest
npm test
pnpm test
```

高风险命令直接审批或拒绝：

```text
rm
del
rmdir
mv
chmod
chown
curl
wget
scp
ssh
git push
git reset --hard
git clean
docker run -v
docker compose down -v
```

默认策略：

```text
unknown shell command -> require approval
```

### 6.4 write_file path guard

`write_file` 目标形态：

```text
write_file(repo_id, relative_path, content)
```

必须禁止：

```text
relative_path = "../other"
relative_path = "C:\\..."
relative_path = "\\\\server\\share\\..."
relative_path = ".git/config"
relative_path = "link_to_outside/secret.txt"
```

写文件时：

1. `relative_path` 禁止绝对路径、盘符、UNC。
2. resolve 后必须在 repo root 内。
3. 父目录不能是 symlink/junction。
4. 如果目标已存在，目标不能是 symlink。
5. 禁止写 `.git` 目录。

## 7. 审批执行链路

### 7.1 第一版不用 LangGraph interrupt

当前第一版采用：

```text
turn A
  -> 发现需要审批
  -> 创建 approval_request
  -> 写 assistant message: 需要你审批
  -> turn A completed 或 waiting_approval

user approves
  -> approval_request.status = approved
  -> 创建 turn B
  -> turn B 消费 approval_request
  -> 执行被批准动作
  -> approval_request.status = applied/consumed/failed
```

这比直接 interrupt/resume 更稳：

- 不依赖 checkpoint。
- 不恢复过期上下文。
- 飞书/API/CLI 能共用审批事实。
- 崩溃恢复只需要查 `approval_requests`。

### 7.2 turn 状态建议

第一阶段：

- `approval_requests` 是事实源。
- turn A 可以保持 `completed`，assistant message 明确等待审批。
- conversation session state 设置 `waiting_for=approval`。

第二阶段：

- 扩展 `turns.status=waiting_approval`。
- `/status` 展示 pending approvals。
- 审批决策后创建新 turn 消费请求。

第三阶段：

- 接入 LangGraph interrupt/checkpoint。
- 仍然保留 `approval_requests` 表作为业务事实源。

### 7.3 审批消费规则

规则：

- 只有 `approved` 可以进入 `applying` 或 `consuming`。
- apply/consume 前必须重新校验 scope、repo policy 和当前 grant。
- 长期授权成功后状态改为 `applied`。
- 一次性动作成功后状态改为 `consumed`。
- 同一个 approval request 不能被两个 turn 消费。
- 失败时状态改为 `failed`，记录 `last_error`。
- 危险动作失败后不自动回到 `approved`。

一次性动作事务边界：

```text
begin transaction
  select approval_request for update
  assert status = approved
  mark status = consuming, consume_turn_id = current_turn_id
commit

execute approved action

if success:
  mark consumed
else:
  mark failed, last_error = ...
```

长期授权事务边界：

```text
begin transaction
  select approval_request for update
  assert status = approved
  mark status = applying
commit

canonicalize + validate path
create repository
create repository_grant
mark applied
```

## 8. API 与交互设计

### 8.1 Repository API

建议新增：

```text
GET /repositories
GET /repositories/{repo_id}
POST /repositories
PATCH /repositories/{repo_id}
POST /repositories/{repo_id}/disable
```

第一版可以只实现：

```text
GET /repositories
POST /repositories
```

`POST /repositories` 必须是受信接口，不能由 LLM 自动调用完成授权，并且必须执行 repo root policy。

### 8.2 Approval API

建议新增：

```text
GET /approval-requests
GET /approval-requests/{approval_id}
POST /approval-requests/{approval_id}/approve
POST /approval-requests/{approval_id}/reject
```

批准 repo access 时：

```text
POST /approval-requests/{id}/approve
  -> approval_requests.status = approved
  -> canonicalize + validate requested path
  -> create repository
  -> create repository_grant
  -> approval_requests.status = applied
  -> create follow-up turn or wait for user next message
```

### 8.3 飞书交互

飞书卡片只做展示和决策入口，底层仍然必须落库到 `approval_requests`。

卡片展示：

```text
Jarvis 请求访问本地仓库

路径：G:\project-a
标准化路径：G:\project-a
权限：coder
repo_id：project-a
原因：用户要求修改该仓库代码
有效期：30 分钟

[批准] [拒绝]
```

按钮回调：

```text
Approve -> /approval-requests/{id}/approve
Reject  -> /approval-requests/{id}/reject
```

## 9. Codex 工具改造

### 9.1 当前状态

当前 `delegate_to_codex` 已经具备：

- `codex exec --json`
- 干净 stdout
- raw JSONL artifact
- preflight/postflight
- `allow_commit` / `allow_push` 硬校验

但它仍然接收 `workdir`。

### 9.2 下一步改造

新增参数：

```text
repo_id
```

执行前：

```python
repo = resolve_repo_from_args(repo_id=args.get("repo_id"), workdir=args.get("workdir"))
authorization = ToolGate.authorize(..., repo_id=repo.repo_id, tool_name="delegate_to_codex")
request.workdir = str(repo.canonical_root_path)
```

拒绝规则：

- repo 不存在：拒绝或创建 `repo_access` approval。
- repo status 不是 active：拒绝。
- 没有 active grant：拒绝。
- repo permission/capability 不足：拒绝或创建 approval。
- workdir 与 repo_id 不一致：拒绝。
- 只有 workdir 命中 active repo：允许但返回 deprecation warning。
- 未授权 workdir：拒绝或创建 approval，不执行。
- `allow_push=true`：必须存在单次 `git_push` approval。
- `allow_commit=true`：至少需要 `git_commit` capability。

### 9.3 tool_call 审计

`tool_calls.input` 应保留：

```json
{
  "repo_id": "jarvis",
  "instruction": "...",
  "allow_commit": false,
  "allow_push": false
}
```

不建议长期保存裸绝对 `workdir` 作为主要审计标识。

artifacts 可记录：

```text
repo_uid:<uuid>
repo_id:jarvis
repo_root:E:\pythonProject\jarvis
codex_events:<path>
git_commit:<sha>
```

## 10. 第一版最小可落地方案

完整 v1.1 是长期安全设计，不代表第一版要全部实现。第一版目标应该收窄为：

```text
Jarvis 知道哪些 repo 可操作。
Codex 只能操作这些 repo。
```

也就是先实现 `Local Repository Registry MVP`，暂不实现完整审批系统。

### 10.1 MVP 目标

MVP 只解决一个核心问题：

```text
delegate_to_codex 不能再自由使用任意 workdir。
```

成功标准：

- Jarvis 默认知道自己的仓库：`repo_id=jarvis`。
- `delegate_to_codex` 优先使用 `repo_id`。
- `workdir` 只作为兼容参数存在。
- 未注册的 `workdir` 一律拒绝，不自动执行。
- `repo_id + workdir` 不一致一律拒绝。
- 当前不做飞书审批、不做多用户授权、不做 LangGraph interrupt。

### 10.2 MVP 数据结构

MVP 可以先不用数据库，使用本地配置或 JSON 文件：

```json
{
  "repositories": [
    {
      "repo_id": "jarvis",
      "name": "Jarvis",
      "root_path": "E:\\pythonProject\\jarvis",
      "canonical_root_path": "E:\\pythonProject\\jarvis",
      "permission_level": "coder",
      "status": "active"
    }
  ]
}
```

如果直接落数据库，也只需要最小字段：

```sql
CREATE TABLE jarvis.repositories (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    repo_id VARCHAR(128) NOT NULL UNIQUE,
    name VARCHAR(255) NOT NULL,
    root_path VARCHAR(1024) NOT NULL,
    canonical_root_path VARCHAR(1024) NOT NULL,
    status VARCHAR(32) NOT NULL,
    permission_level VARCHAR(32) NOT NULL,
    created_at DATETIME(6) NOT NULL,
    updated_at DATETIME(6) NOT NULL,
    UNIQUE KEY uk_repositories_canonical_root_path (canonical_root_path)
);
```

长期字段如 `repo_uid`、`path_hash`、`repository_grants`、`source_approval_id` 可以后续补。

### 10.3 MVP RepositoryRegistry

MVP 服务接口：

```python
class RepositoryRegistry:
    def list_repositories(self) -> list[RepositoryRef]: ...
    def resolve_repo(self, repo_id: str) -> RepositoryRef: ...
    def find_by_workdir(self, workdir: Path) -> RepositoryRef | None: ...
```

`RepositoryRef`：

```python
class RepositoryRef:
    repo_id: str
    name: str
    root_path: Path
    canonical_root_path: Path
    status: str
    permission_level: str
```

MVP 可只支持：

```text
status = active
permission_level = coder
```

### 10.4 MVP path policy

MVP 不做完整 Windows junction/submodule/worktree 支持，只做保守校验：

- path 必须存在。
- path 必须是目录。
- path 不能是磁盘根目录。
- path 不能是用户主目录。
- path 不能是明显系统目录。
- 默认要求 path 是 git repo root，即存在 `.git`。

如果不满足，不能注册为 repo。

### 10.5 MVP delegate_to_codex 行为

`delegate_to_codex` schema 兼容期：

```text
repo_id?: string
workdir?: string
instruction: string
verification_cmd?: string
allow_commit?: boolean
allow_push?: boolean
```

解析规则：

| 输入 | 行为 |
|------|------|
| `repo_id=jarvis` | 使用 registry 中的 Jarvis root |
| `repo_id=jarvis + workdir=Jarvis root` | 允许，返回 workdir deprecation warning |
| `repo_id=jarvis + workdir=其他路径` | 拒绝 |
| 只有 `workdir=Jarvis root` | 允许，但返回 deprecation warning |
| 只有 `workdir=未注册路径` | 拒绝 |
| `repo_id=unknown` | 拒绝 |

MVP 阶段不自动创建 approval request，只返回清晰错误：

```text
Repository is not registered or not authorized. Ask the user to register this repository first.
```

### 10.6 MVP 不做什么

MVP 明确不做：

- 不做 `repository_grants` 表。
- 不做多用户、多 conversation subject 授权。
- 不做完整 `approval_requests`。
- 不做飞书审批卡片。
- 不做 shell/write_file 全量 repo gate。
- 不做 symlink/junction/submodule/worktree 完整支持。
- 不做 LangGraph interrupt。
- 不做自动注册未知路径。

### 10.7 MVP 测试

必须覆盖：

- 默认 `jarvis` repo 可 resolve。
- `delegate_to_codex(repo_id=jarvis)` 使用 registry root。
- `delegate_to_codex(workdir=jarvis_root)` 兼容允许但有 warning。
- `delegate_to_codex(workdir=unknown)` 拒绝。
- `delegate_to_codex(repo_id=jarvis, workdir=unknown)` 拒绝。
- `repo_id=unknown` 拒绝。
- 未注册路径不会执行 Codex subprocess。

### 10.8 MVP 飞书验证方式

MVP 阶段不做完整飞书审批卡片，但必须能通过飞书验证 repo registry 和 Codex gate 是否生效。

验证目标：

```text
用户在飞书里只能让 Jarvis 操作已注册 repo。
未注册 repo、未知 repo_id、repo_id/workdir 不一致都不能触发 Codex 执行。
```

建议先支持几个只读状态命令：

```text
/repos
/repo jarvis
/repo status
```

返回示例：

```text
已授权仓库：

- jarvis
  路径：E:\pythonProject\jarvis
  权限：coder
  状态：active
```

Codex 验证用例：

1. 正常路径：

```text
请在 jarvis 仓库里检查 tests/test_tools_codex.py，不要改代码，只总结这个测试覆盖了什么。
```

期望：

- LLM 使用 `delegate_to_codex`。
- tool args 使用 `repo_id=jarvis`。
- Codex workdir 来自 registry。
- 回复里说明执行仓库是 `jarvis`。

2. 未知 repo：

```text
请在 repo_id=unknown 的仓库里跑测试。
```

期望：

- 不执行 Codex。
- 返回清晰错误：

```text
仓库 unknown 未注册，Jarvis 不能访问。请先注册该仓库。
```

3. 未授权本地路径：

```text
请访问 G:\some-project 并修改代码。
```

MVP 期望：

- 不执行 Codex。
- 不自动注册。
- 返回：

```text
该路径尚未注册为 Jarvis 可操作仓库，MVP 阶段需要先由受信接口注册。
```

4. 当前仓库测试：

```text
请在 jarvis 仓库运行 uv run pytest tests/test_tools_codex.py -q，不要提交。
```

期望：

- 使用 `repo_id=jarvis`。
- `allow_commit=false`。
- `allow_push=false`。
- Codex 执行后 stdout 不包含 raw JSONL。
- 回复包含测试结果和权限校验摘要。

5. push 风险：

```text
请在 jarvis 仓库 git push 到远端。
```

MVP 期望：

- 不执行 push。
- 如果调用 Codex，`allow_push=false`。
- 如果 Codex 造成 upstream 变化，ToolExecutionResult 必须失败。
- 最好由 runtime policy 直接拒绝或说明“git push 需要后续单次审批功能”。

飞书验证需要记录：

- conversation_id
- turn_id
- tool_calls.tool_name
- tool_calls.input.repo_id
- tool_calls.status
- tool_calls.output 中的 repo/permission 摘要

如果飞书消息渲染支持 `/status`，应展示：

```text
当前会话状态：
- waiting_for: none
- active_repo: jarvis
- last_tool: delegate_to_codex
- last_tool_status: completed / rejected / failed
```

MVP 不要求飞书按钮审批；完整审批卡片进入后续 `Repo Access Approval` 阶段。

## 11. 第一版后续扩展

第一版不要一次性覆盖所有审批类型。MVP 之后再进入完整审批和授权模型。

### 11.1 表

```text
repositories
approval_requests
```

`repository_grants` 可以先不落表，但字段和服务接口要按 grant 模型设计，避免后续迁移困难。

### 11.2 工具

先只改：

```text
delegate_to_codex
```

shell/write_file 后续进入 repo gate。

### 11.3 规则

```text
1. Jarvis 自己默认注册为 repo_id=jarvis。
2. delegate_to_codex 优先使用 repo_id。
3. workdir 兼容但必须命中 active repo。
4. unknown repo_id 直接拒绝或创建 repo_access approval。
5. allow_push 永远需要单次审批。
6. allow_commit 默认 false；开启时至少需要 git_commit capability。
```

### 11.4 审批类型

第一版只支持：

```text
repo_access
git_push
```

暂时不要把 `shell_command`、`file_write`、`destructive_operation` 全做完，避免第一版复杂度过高。

## 12. 实施计划

### Phase 1：Repository Registry + Path Canonicalization

- 新增 `repositories` 表或先用本地 JSON 配置。
- 增加 `repo_uid`、`canonical_root_path`、`path_hash`。
- 默认注册当前 Jarvis 仓库。
- 新增 `RepositoryRegistry` 服务。
- 实现 `resolve_repo(repo_id)`。
- 实现 repo root policy。

### Phase 2：Codex repo_id 接入 + 禁止未授权 workdir

- `delegate_to_codex` schema 增加 `repo_id`。
- `repo_id` 优先，`workdir` 仅作为兼容参数。
- 未授权 workdir 拒绝。
- workdir 命中 active repo 时允许但产生 warning。
- 测试覆盖 repo_id 正常解析、workdir 未授权拒绝、repo_id/workdir 不一致拒绝、workdir 兼容 warning。

### Phase 3：Tool Gate 统一封装

- 新增 ToolGate。
- Codex 执行前强制走 ToolGate。
- shell/write_file 先设计接口，后续接入。
- deterministic shell allowlist/blocklist 先落代码。

### Phase 4：Approval Request 事实源

- 新增 `approval_requests` 表。
- 新增 ApprovalService。
- 实现 create / approve / reject / apply / consume / fail。
- 保存 `resume_payload`、`idempotency_key`、`risk_level`、`last_error`。
- 第一版审批后由新 turn 消费，不使用 LangGraph interrupt。

### Phase 5：Repo Access Approval 流程

- 未授权 path 创建 `repo_access` approval。
- 飞书或 API 展示审批请求。
- 用户批准后重新 canonicalize + validate path。
- 写入 `repositories`，后续再拆 `repository_grants`。

### Phase 6：shell/write_file 进入 repo gate

- shell 工具支持 repo_id。
- write_file 支持 repo_id。
- 所有路径 resolve 后必须在 repo root 内。

### Phase 7：高风险操作审批

- `git_push` 单次审批。
- `destructive_shell` 单次审批。
- `secret_file_read` 默认拒绝或单次审批。

### Phase 8：LangGraph interrupt 可选接入

- `approval_requests` 仍然作为事实源。
- interrupt 只负责暂停 graph。
- approval 决策后可以选择 resume 原 graph 或创建新 turn。

## 13. 测试策略

### 13.1 Repository Registry

测试：

- 默认 jarvis repo 存在。
- active repo 可以 resolve。
- disabled/revoked repo 被拒绝。
- repo_id 唯一。
- canonical_root_path 唯一。
- path_hash 唯一。
- 磁盘根目录、用户目录、系统目录拒绝注册。

### 13.2 Path Gate

测试：

- repo 内路径允许。
- `..` 逃逸拒绝。
- 绝对路径在 repo 外拒绝。
- repo_id/workdir 不一致拒绝。
- Windows 盘符和大小写标准化。
- `.git` 目录写入拒绝。
- symlink/junction 父目录拒绝。

### 13.3 Approval Request

测试：

- 创建 pending approval。
- approve 后状态变 approved。
- reject 后不能 apply/consume。
- consumed 后不能重复消费。
- expired 不能 approve。
- repo_access approve 后创建 repository。
- apply/consume 失败时记录 failed + last_error。
- idempotency_key 防止重复创建审批。

### 13.4 Tool Gate

测试：

- Codex 没有 repo grant 时拒绝。
- Codex 有 coder grant 时允许。
- `allow_push=true` 没有单次审批时拒绝。
- unknown shell command 要求审批。
- blocklist shell command 要求审批或拒绝。

### 13.5 Runtime

测试：

- 未授权路径请求不会执行工具。
- 未授权路径会生成 approval request。
- 当前 turn 返回等待审批消息。
- 批准后新 turn 消费 approval request。
- 拒绝后新 turn 不执行工具。

## 14. 关键决策

1. `repositories` 是仓库资源事实源。
2. `repository_grants` 是授权关系事实源；第一版可折叠，但接口按 grant 设计。
3. `approval_requests` 是审批事实源，不依赖 LangGraph interrupt。
4. ToolGate 是执行级安全边界，必须先于工具执行。
5. 当前第一版不恢复同一个 graph node，而是批准后创建新 turn 消费审批。
6. LLM 不应该自由传绝对路径；目标形态是只传 `repo_id`。
7. Jarvis 自己也是一个 repo：`repo_id=jarvis`。
8. repo access 可以是长期授权；git push、destructive operation、secret read 应按次审批。
9. 即使未来接入 LangGraph interrupt，审批表也不能省。
10. shell 风险分类必须有 deterministic guard，不能只靠 LLM 判断。

## 15. 与现有设计的关系

本设计补齐以下设计里的开放项：

- `Jarvis 长运行多轮对话 ReAct Agent 设计` 中的 `permission_requests`。
- `Jarvis 轻量会话强化与 Long Run 演进设计` 中的 `waiting_for=approval`。
- `Jarvis Codex Coder 工具接入设计` 中的 repository workflow 权限边界。

本设计不要求立即引入重型 long-run graph。它优先让仓库权限、工具 gate 和审批成为可查询、可审计、可恢复的业务事实。
